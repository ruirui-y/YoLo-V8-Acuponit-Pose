二、系统架构总览

通信原则（8-13 架构决策）：

  • 服务间通信（gateway ↔ paymentservice）= 同步 gRPC（请求-响应就该同步，不用 MQ 绕圈）
  • 外部中台交互 = 异步 Webhook（支付回调本质，废不掉）
  • 同步归同步、异步归异步

paymentservice 内部组件（架构图里的简化）：

  • PaymentServer gRPC（9001）—— 业务入口
  • MidPlatformClient —— 中台 HTTP 客户端（同步阻塞）
  • NotifyServer（8183）—— 中台 Webhook 回调接收（独立 HTTP 服务器）
  • OrderService —— 超时订单巡检（独立线程 + steady_timer）
  • 所有组件共享 MySQL（t_pay_order / t_user_wallet / t_point_flow / t_goods_sku）

三、正向链路：创建订单（同步 gRPC）

入口：PaymentServer::CreateOrder（PaymentServer.cpp），user_id 走 gRPC metadata （gateway 侧 ctx.AddMetadata("user_id", ...)，服务端 GetUserIdFromMetadata 取，不放消息体）。

步骤细节：

失败语义：商品不存在 NOT_FOUND；中台/token/二维码失败 UNAVAILABLE；写库失败 INTERNAL。 ②已写库但 ③④ 失败时，订单留在 status=0，由巡检兜底关单（有意设计，不主动删单，保留账目痕迹）。

四、反向链路：支付回调（异步 Webhook）

中台支付成功后按 callbackUrl 回拨 NotifyServer（8183，POST /api/wechat/pay_notify）。

NotifyServer 处理（先回 200 再处理）：

  1. 立即回 200（防中台超时重试）
  2. 解析 outTradeNo / transactionNo / paymentStatus —— 全部 contains + is_null 防御
  3. 直接传支付状态 + 流水号（不再映射成 bool），流水号为空时由 ProcessPaymentResult 内部查单兜底

五、支付结果处理：ProcessPaymentResult（核心，三入口共用）

xxxxxxxxxx
int64_t ProcessPaymentResult(const std::string& order_id,
    int payment_status, const std::string& transaction_no)

三个入口：gRPC NotifyPaid / Webhook NotifyServer / 巡检补积分 —— 全部走这一个幂等入口。

执行流程：

xxxxxxxxxx
ProcessPaymentResult(order_id, status, tx)
│
├─ ① 流水号为空？
│     ├─ 是 → CheckOrder 重新查单：
│     │       查单成功 → 流水号 + 支付状态都重置为查单结果（以查单 API 为准）
│     │       查单失败(ERROR) → 保留传入状态，WARN
│     └─ 否 → 用传入的 status + tx
│
├─ ② status != SUCCESS → UPDATE 关单（status 0→-1），返回 0
│
└─ ③ status == SUCCESS：
     查订单（status=0，不存在则幂等返回 0）
     → 单事务：
         UPDATE t_pay_order SET status=1, pay_time=NOW(),
                third_party_no = NULLIF(?, '')       -- 流水号原子落库，空自动 NULL
         WHERE order_id=? AND status=0                -- 幂等条件
         UPDATE t_user_wallet SET balance_points=+reward, total_recharged=+reward
         INSERT t_point_flow(FLOW_RECHARGE, +reward, balance_after=子查询)
     → 返回最新余额

幂等设计（三保险）：

  • 所有 UPDATE 带 AND status=0 —— 重复回调/并发回调只生效一次
  • 单事务 —— 订单/钱包/流水要么全成要么全败
  • third_party_no = NULLIF(?, '') —— 流水号空自动写 NULL（不污染对账字段），非空原子写入

gRPC NotifyPaid 调用：OrderNotifyPush 无流水号字段（proto 确认）→ 传空串，内部查单兜底。

十三、本地联调方法（模拟回调，不依赖中台）

中台回调发到公网服务器而非本地，局域网测试收不到真回调 —— 用 curl 模拟回调即可完整测试回调链路：

xxxxxxxxxx
curl -X POST http://127.0.0.1:8183/api/wechat/pay_notify -H "Content-Type: application/json" -d "{\"outTradeNo\":\"PAY_xxx\",\"paymentStatus\":2,\"transactionNo\":\"STG20260814001\"}"
  • paymentStatus: 2 = SUCCESS → 加积分 + 流水号落库
  • paymentStatus: 0 = UNPAID → 关单
  • 去掉 transactionNo → 触发内部查单兜底（需中台可达）
  • 验证点：日志 收到支付回调 + 支付完成，DB 订单 status=1 / third_party_no / pay_time

注意：curl 命令在 cmd 用 \" 转义 JSON 引号；PowerShell 用 curl.exe + 单引号；bash 用单引号 + \ 续行。

十四、架构决策备忘（面试口径）

  1. 两种异步分离：服务间同步 gRPC，外部中台异步 Webhook —— 同步归同步、异步归异步
  2. 幂等三保险：status 条件更新 + 单事务 + 巡检兜底
  3. 先回 200 再处理：回调响应与业务处理解耦，中台不重试
  4. 以查单 API 为最终依据：流水号为空时查单重置状态+流水号（查单失败保留传入，防误降级）
  5. 账目不删只关：失败订单置 -1/-2 保留痕迹，3 天后才物理清理
  6. user_id 走 gRPC metadata：业务消息体保持干净，鉴权信息由网关注入
  7. thread_local SqlExec：每 gRPC worker 线程独立连接池，无锁无共享（项目明确不改为全局共享）
  8. JSON null 防御铁律：中台/回调响应字段为 null 是常态语义，所有解析 contains + is_null，禁止裸 .value()
